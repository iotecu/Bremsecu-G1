# BREMSECU G1 — LANGUAGE / i18n AUTHORITY

Status: **FINAL**
Role: Mandatory pre-implementation contract for the PWA

The PWA is multilingual and must support all 14 languages below. i18n is established before screen implementation, not added later.

| 1 | Türkçe | `tr` | LTR | Canonical source, default and fallback |

| 3 | Deutsch | `de` | LTR | Target locale |
| 4 | Français | `fr` | LTR | Target locale |

No implementation agent may reduce or reorder this approved language list in the selector.

## 2. Blocking initialization rule

Before approved screen implementation begins:

1. Create the i18n runtime and locale registry.
2. Create all 14 locale files.
3. Complete the Turkish source dictionary for the implemented scope.
4. Implement persistent language selection.
5. Implement and verify Arabic/Persian RTL behavior.
6. Include all locale files in the offline application/cache strategy.
7. Add an automated locale key-parity check.
8. Remove component-level hard-coded user-facing strings.

The screen implementation phase is blocked until this foundation works.

## 3. Source and fallback authority

- Turkish (`tr`) is the semantic source, initial default and runtime fallback.
- All target locales use exactly the same key tree as Turkish.
- A missing target-locale key falls back to Turkish; the UI must never display an empty value, raw key or `undefined`.
- A locale is not production-complete while it has missing Turkish source keys.
- Automated checks must compare every target locale against the Turkish key set and fail on missing keys.

Equivalent TypeScript locale modules are acceptable if required by the existing PWA toolchain, but separate locale resources, identical key trees and the rules in this document remain mandatory.

Use stable semantic keys, not full display sentences as keys.

## 5. No hard-coded UI text

All user-facing content must pass through the i18n layer, including:

- titles, descriptions, labels and buttons;
- modal and safety-warning text;
- PASS/FAIL and other visible status labels;
- form fields, placeholders and validation messages;
- reports, settings and battery labels;
- toast, connection, warning, fault and error messages;
- accessibility labels and image alternative text.

Dynamic vehicle data, plate/chassis values, measurements and technician-entered notes are not translated.

## 6. UI behavior

- The language badge in the top brand bar opens the language selector.
- The selector displays the native labels in the canonical order above.
- The selected language is highlighted.
- Language changes apply immediately to the full PWA without reloading.
- The chosen language persists across page reloads and device reconnects.
- Changing language must not reset an active service record, test state or live measurements.
- Language selection must not alter diagnostic logic, pin identities, thresholds or safety interlocks.

## 7. Firmware / language boundary

The ESP32 firmware does not provide translated user sentences. HTTP/WebSocket payloads carry stable machine data such as:

- IDs, types, status codes and enum values;
- numbers, booleans, timestamps and measurement values;
- pin, channel, test, warning and fault identities.

The PWA maps those identities to the selected locale. API field names, enums, endpoint paths and event names must never change with the UI language.

## 8. Fixed technical identities

Keep these unambiguous and unchanged across languages:

- `BREMSECU`
- `ISO 7638`
- `ISO 12098`
- `CAN H`
- `CAN L`
- pin numbers
- API routes and JSON field names
- WebSocket event names
- test/channel IDs and enum values

Turkish UI terminology uses `TERMİNASYON`. Other locales use the correct technical equivalent for the language while the machine identity remains unchanged.

Raw API voltage unit remains `V`. Display formatting may use `В` in Russian UI where linguistically appropriate; this does not modify the payload.

## 9. Directionality

Arabic (`ar`) and Persian (`fa`) set `dir="rtl"` at the application root.

- RTL is a layout behavior, not only right-aligned text.
- Directional controls/icons adapt where required for reading and navigation.
- Numeric electrical values, ISO identities, CAN H/CAN L, pin numbers and physical connector mapping must not be mirrored in a way that changes technical meaning.
- The diagnostic hierarchy and approved visual structure remain consistent.

## 10. Offline requirement

- All locale resources ship with the static application.
- Locale files and required fonts are included in the Service Worker cache/application package.
- Changing language after installation requires no internet access.
- Runtime cloud translation and external translation APIs are forbidden.
- All languages must work while connected directly to the ESP32 hotspot.

## 11. Translation quality

- Use automotive/heavy-vehicle terminology, not literal word-for-word translation.
- Safety warnings are concise, direct and imperative.
- One concept uses one consistent term throughout a locale.
- Button labels remain suitable for the approved mobile geometry.
- Variables use placeholders/interpolation, not sentence concatenation.
- Plurals, dates, times and numbers use locale-aware formatting available offline in the browser.

## 12. Acceptance gate

- [ ] exactly 14 locales exist in the approved order;
- [ ] all locales have key parity with Turkish;
- [ ] Turkish is source, default and fallback;
- [ ] language selection is persistent and does not reset operational state;
- [ ] Arabic and Persian RTL layouts work correctly;
- [ ] all languages work with external internet disabled;
- [ ] no user-facing component text bypasses i18n;
- [ ] build/test fails on a missing locale key;
- [ ] firmware/API technical identities remain language-independent.
